Пример 13. Горизонтальный шардинг таблицы пользователей

Ситуация. Таблица users содержит 400 млн записей и не помещается на одном сервере. Применим горизонтальный шардинг по правилу из лекции.

  1. На серверах S1 и S2 создаём одинаковую таблицу users (только структуру).
  2. Правило выбора сервера: id % 2 == 1 → S1 (нечётные), id % 2 == 0 → S2 (чётные).
  3. Перед каждым запросом приложение вычисляет сервер: пользователь с id = 1057 — нечётный, значит, обращаемся к S1; id = 2024 — к S2.

Добавим отказоустойчивость. Для каждого шарда настраиваем репликацию master–slave: S1 → S1-slave, S2 → S2-slave. Чтение (SELECT) можно выполнять на slave-серверах, а при отказе мастера переключиться на slave.

Ограничение. Если позже понадобится третий сервер, правило «чёт/нечет» придётся заменить (например, на id % 3) и перераспределить данные — шардинг выполняется в приложении и зависит от структуры БД.

Пример 14. Выбор между согласованностью и доступностью (CAP)

Рассмотрим две системы, работающие на нескольких дата-центрах; связь между дата-центрами может прерываться (разделение сети неизбежно, значит, P нужно обеспечить).

  • Банковские переводы → CP. Если дата-центры потеряли связь, лучше временно отказать в операции, чем допустить, чтобы один и тот же остаток был списан дважды. Жертвуем доступностью.
  • Счётчик лайков в соцсети → AP. Пользователь всегда должен видеть страницу; если в одном дата-центре показано 1520 лайков, а в другом 1523, это допустимо: данные станут согласованными позже (eventually consistent). Жертвуем согласованностью.

Вывод. Выбор между C и A при разделении сети определяется требованиями предметной области; большинство NoSQL-систем выбирают AP.
